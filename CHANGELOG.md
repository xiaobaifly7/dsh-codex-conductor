`0.9.123` 的失败回执给出失败原因、尝试次数、记录的改动文件数及下一步。规划端按失败类别处理，避免连续原样重派。模型拒绝保持终态。runner 处理超时前已入队的完成事件，避免把已收到的完成结果误判为超时。

`0.9.122` 的 `runnerAgentsMd: bundled` 可选用随包附带的短版执行指令，默认仍沿用用户文件。派单可用 `must_verify` 标记必须实测的验收项，核验优先覆盖，结案记 `met` 须有独立核验结果。本版首次加载后记录的返工欠账跟踪到后继轮复核通过，Goal 完成时提醒干净但未复核的写入任务。新增默认关闭的 `modelAB`，按新线程的任务号确定模型，续接保留原分配。新增只读对照脚本 `tools/model_ab_stats.py`。

`0.9.121` 改写派单和执行提示。规划端按可独立验收的结果拆单，派单前核对写入权限、运行前置和本轮可取得的证据。执行端遇到方法不可用时，在原授权内换等价方法，区分实测不符的 `not_met` 和缺前置的 `blocked`，并明确关键观测、清理或恢复失败须以非零状态退出。

`0.9.120` 让核验能与下一单并行，并少拒结案验收。之前收尾护栏只要有已结束未验收的任务就拒绝开新工作的 `codex_run`，而结案依据规则要它先核验，于是规划端只能干等核验结束；`verify_previous` 本身是 `codex_run` 的参数，同样被拒，正好在它要解决的场景里用不上（0.9.118 上线后 8 次核验 0 次走 verify_previous，同会话并行为 0）。现在本会话唯一一个待验收任务正在核验（它的第一次核验在跑，或本单带 `verify_previous` 核验它）且没有别的待收尾任务时，放行写入范围不与它重叠的新任务；每个任务只放行一次，核验结束后照常要先验收；靠 `verify_previous` 放行且设了 `maxRunningJobs` 时要放得下两单；结果带 `closeout_deferred`，`codex_runtime` 计 `deferred_dispatch`。缺依据的拒绝和收尾护栏的拒绝都写明这条路。`accepted_deviations` 里保留未满足却没写 `accepted` 的条目，按接受未满足处理（原因取 evidence，带“（按 evidence 推定）”前缀，结果里的 `review_fixes` 说明，照样经过用户确认），不再拒绝；从不推定 met。`codex_runtime` 补上 `met_planner_level` 和 `accepted_inferred`。

`0.9.119` 补上 0.9.118 上线后发现的两处缺口。报告多出的行：报告行数与验收条数不同时（核验报告几乎都是这样），不再按位置把报告行对到验收编号；自标 `blocked` / `not_met` 又对不上任何验收原文的行，结案结论必须在新字段 `report_rows`（`{row, status, evidence, accepted?}`）逐行处理，规则与 `criteria` 相同——记 met 要独立依据，保留未满足要在 `accepted_deviations` 里写 `accepted`；之前只按验收条数提交就能结案，这些行没人处理。核验报告只有对得上核验项的行才算依据（之前条数不同时按位置取行，抽查行会被当成某条原验收的结论）；对不上验收清单的自标未满足行，核验任务单列一条。核验任务的提示改为一条验收只回报一行、抽查结论写进第 3 条的 evidence；所有任务的提示写明 criteria 条数与验收标准相同。`accepted`：`codex_review` 的参数 schema 之前没有声明 `accepted`（条目 `additionalProperties: false`），规划端按 schema 写不出这个字段，“未满足但接受”实际用不了；现已声明，描述里也写明用法。被拒时的骨架给 `accepted_deviations` 里保留未满足的条目带上 `accepted`（沿用已填的，否则留占位），未填的占位单独提示并给出一行结构示例，改记 met 或 needs_changes 时自动去掉。runner 的 `validate_review` 接受 `report_rows`，`summary` 的 `accepted_open` 也列出接受的报告行。

`0.9.118` 修复 0.9.114 的结案依据规则在实际运行中从未生效：runner 的 `status` 输出不带 `finished_at`，截止判断因此把每个任务都当成截止之前结束、一律按 planner 规则结案，`criterionSupport` 从未运行。现在 `status` 与任务列表一样带 `started_at` / `finished_at`；拿不到结束时间时按任务号里的开始时间判断，只有明显早于截止时间（任务号时间加 14 小时仍早于截止）的才按 planner 规则，新任务和说不准的都按 independent。用户回复依据（以及接受偏差的用户确认）不再把插件自己代发的消息（续接、send-request，`source.via` 标记）和看门狗补发的“继续”当作用户回复；宿主提问的自动代答本来就不算。planner / off 级别下把自标未满足的条目记成 met 的结案，计为 `met_planner_level`，不再混进 `all_met`。端到端测试用从真实 runner status 输出脱敏的样本。

`0.9.117` 新增 `mcpWriteAllow`（默认 `[]`）。名单内的 MCP 工具可通过动作名的写入和执行检查，也计入白名单模式。可用于让规划端直接调用 draw.io 绘图，其他护栏规则照常生效。

`0.9.116` 同一宿主进程热重载时，记录卸载前仍在运行的回合。默认等 20 秒后复核并续上符合条件的中断回合，连续重载会接着处理剩余名单。缺少卸载记录时，只在确认同进程重载后检查最近 10 分钟的中断。`autoResume.reloadDelaySeconds: 0` 关闭此功能，结果以 `trigger: "reload"` 记录。

`0.9.115` 新增 `autoAnswer`。宿主提问默认等 10 分钟后按推荐代答，支持多选、自由文本和多题。高风险与排除项保留给用户。Codex 指挥面板显示等待和历史，支持立即按推荐回答或取消单条代答。热重载保留提出时间，已超时的恢复提问另等 30 秒。

`0.9.114` 结案质量：Codex 报告自标 `blocked` / `not_met` 的验收项，结案（`verified` 和 `accepted_deviations` 一样）记成 `met` 时，默认（`closeoutEvidence: independent`）要有独立依据——晚于该轮结束、核验本单元并把这一条判 met 的核验任务（核验任务现在把每个自标未满足的原验收项单列一条）、同一单元后续轮次报告这一条 met、或原会话用户在作业结束后的真实回复。这收紧了 0.9.103 的规则：那条只管 `verified`、只拦照抄报告原文，规划端自己写的证据就能过；现在它只在 `closeoutEvidence: planner` 下沿用，`off` 不查。缺依据时一次列出三条路（核验、返工、照实记未满足）。新增“未满足但接受”：`accepted_deviations` 的条目可保留未满足状态并写 `accepted` 原因，与接受偏差同一道用户确认，`summary` 的 `accepted_open` 列出。本机首次加载这一版之前结束的任务按 planner 规则结案（`closeout-evidence-since.json`）。结案结果计入 `closeout-stats.json`、`codex_runtime` 显示；任务 context 记 `routing`，收尾护栏拒绝记入 `closeout-refusals.jsonl`。

`0.9.112` 续接开新线程补到 `codex_run`：带 `resume` 且原线程上次请求超过 `continueFreshAboveTokens` 时开新线程，规划端任务原文完整保留、前面附上一轮交接内容，新任务以 `parent_job_id` 挂到该线程上本会话（含交接前任）最新的任务下；`fresh` 可逐次指定；结果写明新旧线程和新任务号；再 resume 已被接替的线程时改接接替线程上最新的任务。`codex_continue` 带 `answers` 默认仍沿用原线程，`fresh: true` 时开新线程、回答写进交接内容。新增 `verify_previous`：`codex_run` / `codex_continue` 派这一单的同时只读核验一个已结束任务，与 `codex_verify` 相同的归属和链接；可写新单的 scope 与被核验任务的 scope 或产物重叠时拒绝；核验没派出时只在结果里说明。写任务起步：scope 整体遍历超过 5 秒时记下最慢的一项。

`0.9.106` 会话交接：长会话每一步都要重发整段历史，越来越慢；现在可以把目标和 Codex 任务转到新会话。在插件状态目录写 `handover-request.json`（`{"sessionId":"…","note":"…"}`），插件用与界面“新对话”相同的 `sessionController.create` 在原工作目录、原预设下新建会话，记录交接（`handover.json`，可成链，原子写入，只有本机请求文件能写），按已有记录机械生成交接单并写到文件，暂停原会话的目标，把交接单作为新会话的首条消息发出，再按剩余轮数为新会话创建同一目标；结果写进 `handover-result.json`。原会话有进行中的回合或运行中的任务时拒绝，`force` 可强制；插件建不了会话时可在界面新建后用 `adopt` 接管；`revert` 撤回。交接后新会话就是原会话任务的归属方：查看、产物读取、验收、续接、核验、取消、`codex_jobs` / `codex_summary` 和收尾护栏都包含原会话的任务（runner `list` / `summary` 新增 `--also-owner`）；原会话只能查看，不能再派活或处理任务，也不会再被任务通知自动唤醒。
